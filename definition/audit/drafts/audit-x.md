## Open Questions

- **1 (operators):** real. `ops(modid)` only licenses an import item; nothing makes `Basics.add` (or `add`) reachable, so `(+)` does not elaborate or evaluate. See X1 (and X5 for `::`).
- **2 (E0 before imports):** static-modules does start every module from the content of E0 (pi_0 with TE_List, VE_List), though it redefines VE_0 rather than citing Appendix C (X10). Dynamic-modules does not: X4.
- **4 (thunk translation):** consistent. Dynamic-core's claim that a `let` group needs only Rec holds, since every member of a recursive `let` component is a function binding (syntax-core restriction, Appendix A Section A.2). The translation respects A25. The stated exception (only function equality) is correct; the residual tension with A59's wording is X15 (minor).
- **5 (A27 three ways):** consistent in intent (every undetermined number variable is Int), but the dynamic side never makes main's Int copy (X6, blocker), drops unused number-polymorphic top-level values (X7), and static-core's main clause is dead and duplicates Dflt (X8).
- **6 (closed types):** the two agree on what an importer sees for header items `T`, `T(..)`, `(..)` and qualified access, but disagree on importing `T(..)` of a closed type (X3), and Appendix D's basis interfaces lack RA and CE altogether (X2).
- **7 (programs):** main not recursive and basis module names reserved are consistent with the rules and rulings but unlogged (X16). The clock (time component, r:p-wait, r:p-proc-sleep) agrees with A81, A70 and effects' statement that Chapter 9 enforces when an action may occur. Safety-only conformance agrees with A61, A86 and A72: resolved.
