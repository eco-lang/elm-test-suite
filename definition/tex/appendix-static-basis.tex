\chapter{The Initial Static Basis}\label{ch:appendix-static-basis}

In this appendix and the next we define a minimal initial basis: the type
names, modules, types and values that the definition itself mentions, together
with all of the module \kw{Basics}. % D4, I1
Libraries may provide richer bases, extending the module environment with
further modules and the interfaces below with further values; such libraries
are not described here. Components of the initial basis are indicated by the
subscript 0. The initial static basis is
\[
  B_0 = T_0, \ME_0, \PE_0, \qquad\text{where}\ \PE_0 = \emptymap,
\]
$T_0$ is given in Section~\ref{sec:appendix-static-basis-tynames} and $\ME_0$
in Sections~\ref{sec:appendix-static-basis-modenv}
to~\ref{sec:appendix-static-basis-platform}. The basis declares no port.

In the type schemes of this appendix a type variable is written as the type
variable of the syntax that names it (Section~\ref{sec:static-core-simple}), so
that its spelling gives its class: \mv{number} has class $\knum$,
\mv{comparable} has class $\kcomp$, \mv{appendable} has class $\kapp$, and
every other variable written here (\mv{a}, \mv{b}, \mv{c}, \mv{d}, \mv{e},
\mv{r}, \mv{x}, \mv{y}, \mv{msg}, \mv{flags}, \mv{model}) has class $\kany$. % A19
No variable of class $\kcapp$ occurs in the initial basis. A type is written as
in Chapter~\ref{ch:static-core}, with type names after their arguments: the
type that a program writes \kw{Maybe a} is $\mv{a}\,\tMaybe$, and \kw{Task x
a} is $(\mv{x}, \mv{a})\sbtTask$.

\section{Type Names}\label{sec:appendix-static-basis-tynames}

The set of type names of the initial basis is
\[
\begin{array}{@{}r@{\ }c@{\ }l@{}}
  T_0 & = & \{\tInt, \tFloat, \tChar, \tString, \tunit, \tList, \tTuple{2},
            \tTuple{3},\\
      &   & \phantom{\{}\tBool, \sbtOrder, \sbtNever, \tMaybe, \sbtResult,
            \tArray, \tBytes, \tValue,\\
      &   & \phantom{\{}\sbtCmd, \sbtSub, \sbtTask, \sbtProcessId,
            \sbtProgram, \sbtNode\}.
\end{array}
\]
The members of $T_0$ are type names, not type constructors; we have spelt each
as a type constructor bound to it in $\ME_0$, or, for $\tunit$ and
$\tTuple{k}$, after the syntax of the types that denote them. Their arities,
and the type constructors bound to them, are shown in
Figure~\ref{fig:static-basis-tynames}. The first eight are the type names of
Figure~\ref{fig:static-core-builtin}, which the rules of
Chapter~\ref{ch:static-core} mention directly. The type names $\tunit$,
$\tTuple{2}$ and $\tTuple{3}$ are bound to no type constructor: the type
expressions \kw{()} and \kw{(}$\,\ty_1\kw{,}\,\ty_2\opt{\kw{,}\,\ty_3}\,$\kw{)}
denote them. Which of the type names are admissible for each class is given by
Figure~\ref{fig:static-core-admissible}: a type built from any type name of
$T_0$ other than $\tInt$, $\tFloat$, $\tChar$, $\tString$, $\tList$,
$\tTuple{2}$ and $\tTuple{3}$ is admissible for no class but $\kany$.

\section{The Module Environment}\label{sec:appendix-static-basis-modenv}

The module environment $\ME_0$ has the domain
\[
\begin{array}{@{}l@{}}
  \{\kw{Basics}, \kw{List}, \kw{Maybe}, \kw{Result}, \kw{String}, \kw{Char},
    \kw{Tuple}, \kw{Array}, \kw{Bytes}, \kw{Debug},\\
  \phantom{\{}\kw{Platform}, \kw{Platform.Cmd}, \kw{Platform.Sub}, \kw{Task},
    \kw{Process},\\
  \phantom{\{}\kw{Json.Encode}, \kw{Json.Decode}, \kw{VirtualDom}, \kw{Html}\}.
\end{array}
\]
The interface $\ME_0(\modid)$ of each module is an environment
$(\emptymap, \TE, \VE)$ whose qualified environment is empty; its type
environment and value environment are shown in
Figures~\ref{fig:static-basis-basics-te} to~\ref{fig:static-basis-effects}.
In Figures~\ref{fig:static-basis-data} to~\ref{fig:static-basis-effects} the
entries of each interface are headed by the name of its module; the bindings
of the type environment come first and, below a rule, those of the value
environment. An interface with no binding shown in a component has the empty
map there; the interfaces of \kw{List} and \kw{Tuple} are $(\emptymap,
\emptymap, \emptymap)$. As in Chapter~\ref{ch:static-core}, every
variable has status $\isv$ and every constructor status $\isc$, and a
constructor of a custom type is bound in the value environment of the
type's structure and, unless the type is closed, in the value environment of
the interface. The type names
occurring in $\ME_0$ are those of $T_0$:
\[
  \tynames \ME_0 \subseteq T_0 .
\]

Every module of $\ME_0$ belongs to the library \kw{elm/core}, except five:
\kw{Bytes} belongs to \kw{elm/bytes}, \kw{Json.Encode} and \kw{Json.Decode}
to \kw{elm/json}, \kw{VirtualDom} to \kw{elm/\allowbreak virtual-dom}, and
\kw{Html} to \kw{elm/html}.
These five are in $\ME_0$ only for their types, which the definition of ports
(Section~\ref{sec:static-modules-ports}) and of the type of \kw{main}
(Chapter~\ref{ch:programs}) mention. % A82, A92, D11

Before any import is read, every module has in scope, unqualified, the type
constructor \kw{List} and the two list constructor names \kw{[]} and \kw{::}
of Section~\ref{sec:static-core-compound}, which no identifier spells. They
form the environment
\[
  E_0 = (\emptymap, \TE_0, \VE_0), \qquad
  \TE_0 = \{\kw{List}\citelabel{b:List} \mapsto (\tList, \VE_0)\},
\]
where
\[
  \VE_0 = \{\kw{[]}\citealso{b:List} \mapsto (\forall\mv{a}.\,\mv{a}\,\tList, \isc),\
           \kw{::}\citealso{b:List} \mapsto (\forall\mv{a}.\,\mv{a} \rightarrow \mv{a}\,\tList
           \rightarrow \mv{a}\,\tList, \isc)\}.
\]
% DECIDED: the List type constructor is in scope in every module before the
% default imports (eco Compiler/Canonicalize/Environment/Foreign.elm:109-121;
% Parse/DefaultImports.elm), and is not exposed by the module List, so it is
% given as E0 rather than in ME0(List). TE_0 and VE_0 are defined here only;
% Chapter 5 starts each module from E0 through pi_0, citing TE_0 and VE_0 for
% the List entries of its provider map (audit X10; decision 2).
The module \kw{List} declares neither the type constructor \kw{List} nor any
constructor, so that \kw{List.List} is not a long type constructor of the
initial basis.

The imports of every module begin with the default imports of
Figure~\ref{fig:default-imports}, which are elaborated
(Chapter~\ref{ch:static-modules}) against $\ME_0$. Every module they name is
in $\Dom\ME_0$, and every type and value they expose is in that module's
interface; an operator they expose is one that the module declares, and
binds nothing. Thus the default imports put in scope, unqualified, every
type, constructor and value of \kw{Basics}; the types \kw{Maybe},
\kw{Result}, \kw{String}, \kw{Char}, \kw{Program}, \kw{Cmd} and \kw{Sub}; and
the constructors of \kw{Maybe} and \kw{Result}. They make every value of
\kw{Debug}, \kw{Platform}, \kw{Maybe} and \kw{Result} available qualified, and
those of \kw{Platform.Cmd} and \kw{Platform.Sub} under the qualifiers \kw{Cmd}
and \kw{Sub}. The modules \kw{Array}, \kw{Bytes}, \kw{Task}, \kw{Process},
\kw{Json.Encode}, \kw{Json.Decode}, \kw{VirtualDom} and \kw{Html} are in scope
only where a module imports them.

\textbf{Operators.} No program declares an operator, so the operators are
those of the initial basis, the same in every program; their fixities are
those of Figure~\ref{fig:core-fixities}. Each is declared, by \kw{Basics} or
\kw{List}, to stand for an identifier. The \emph{static operator table}
\[
  \OTstat : \cls{Op} \finmap \TypeScheme \times \IdStatus
\]
maps each operator of Figure~\ref{fig:core-fixities} to the type scheme and
status of the identifier it stands for, and is given in
Figure~\ref{fig:static-basis-operators}. The meaning of an operator is
$\OTstat(\opv)$, whatever the context (Section~\ref{sec:static-core-projection}):
it is looked up in no environment and reached through no interface, so a
program's own top-level \kw{add} does not capture \kw{+}. The operators of
library modules outside the initial basis are outside the definition.
% A16, A56; audit X1 (decision 1)
The operator \kw{::} stands for the list constructor \kw{::} of $\VE_0$, with
status $\isc$, and is declared by \kw{List}; every other operator is declared
by \kw{Basics}, as the figure records, so that the set of operators that
\kw{List} declares is $\{\kw{::}\}$ and that of \kw{Basics} is
$\Dom\OTstat\setminus\{\kw{::}\}$ (no other module of $\ME_0$ declares an
operator). Every operator other than \kw{::} stands for a variable of \kw{Basics}
(\kw{add}, \kw{eq}, \kw{apR} and the others of the figure) that \kw{Basics}
declares but does not expose. These variables are \emph{hidden}: they are
bound in no interface of $\ME_0$, so that no program can write
\kw{Basics.add} or \kw{add} for \kw{(+)}.

\textbf{Hidden identifiers.} Besides the variables that the operators stand
for, the modules of $\ME_0$ declare the following identifiers, which no
interface binds and no program can name: the constructor \kw{JustOneMore} of
the closed type \kw{Never} of \kw{Basics}; and, in \kw{Task}, the function
\kw{command} and the constructor \kw{Perform} of the custom type \kw{MyCmd},
which \kw{Task} does not expose. In elm/core 1.0.5 that type is declared as
\kw{type MyCmd msg = Perform (Task Never msg)}, so the task that \kw{Perform}
carries cannot fail. These hidden identifiers are mentioned only by the texts of
values of the basis written in Elm, and their values are given in
Section~\ref{sec:appendix-dynamic-basis-elm}. % I2, A60, A85

\textbf{Library functions.} The modules of $\ME_0$ declare, in their
libraries, many values that are absent from the figures, among them every
function of \kw{List}, \kw{String}, \kw{Char}, \kw{Tuple}, \kw{Array},
\kw{Maybe} and \kw{Result}, the functions of \kw{Bytes}, and the encoders,
decoders and views of \kw{elm/json} and \kw{elm/html}. Like the modules not in
$\Dom\ME_0$ (\kw{Dict}, \kw{Set}, \kw{Bitwise}, \kw{Bytes.Encode},
\kw{Bytes.Decode} and the rest), they are library, not language, and lie outside
the definition. The module \kw{Tuple} is in $\ME_0$ only because a default
import names it; its interface is empty. The type \kw{Router} and the values
\kw{sendToApp} and \kw{sendToSelf} of \kw{Platform}, which serve managers,
are omitted with them, effect modules being kernel-only. % A16, A37, I1

\section{Debugging, Programs and Effects}\label{sec:appendix-static-basis-platform}

The interfaces of the remaining modules are shown in
Figures~\ref{fig:static-basis-platform}, \ref{fig:static-basis-task}
and~\ref{fig:static-basis-effects}.
The meanings of the values of \kw{Debug} are given in
Appendix~\ref{ch:appendix-dynamic-basis}. Since the result type of
\kw{Debug.todo} is a bound variable of its type scheme, an application of
\kw{Debug.todo} elaborates to every type. % A62
Chapter~\ref{ch:effects} builds task, command and subscription values from
the values of \kw{Platform.Cmd}, \kw{Platform.Sub}, \kw{Task} and
\kw{Process}, and \kw{Platform.worker} makes a program
(Chapter~\ref{ch:programs}). % D10
The function \kw{command} of \kw{Task} and the constructor \kw{Perform} of its
custom type \kw{MyCmd} are hidden
(Section~\ref{sec:appendix-static-basis-modenv}): they are absent from the
interface of \kw{Task}, and are reached only through the texts of
\kw{perform} and \kw{attempt}, whose environment
(Section~\ref{sec:appendix-dynamic-basis-elm}) binds them. The
values of ports are not in $\ME_0$: a port is declared by a module of a
program (Section~\ref{sec:static-modules-ports}).
The type constructors \kw{Task.Task} and \kw{Process.Id} are type aliases in
their libraries; the type functions they are bound to are the type names
$\sbtTask$ and $\sbtProcessId$ themselves (Section~\ref{sec:static-core-types}),
and likewise \kw{Json.Decode.Value} is bound to $\tValue$ and \kw{Html.Html}
to $\sbtNode$.
