# Standard Elm: mechanisation of the Core dynamic semantics (Lean 4)

A Lean 4 encoding of Chapter 6 of *A Standard Definition of Elm?* (Dynamic
Semantics for the Core, `dynamic-core.tex`) and of the arithmetic, equality,
order, Boolean, conversion, power and elementary-function, append and
character part of APPLY (Appendix D, `sec:appendix-dynamic-basis-apply`), with an executable evaluator proved sound
and complete for the rules, a logged twin of every rule that records `Debug.log` output, and as examples the test programs that accompany the book, translated into Lean
by `definition/tools/src/Translate.elm` (every `elm-spec` test it can translate).

## Build and run

Requires Lean 4.35.0 and Lake (`elan` installs both; put `~/.elan/bin` on the
PATH). From this folder:

```
lake build && lake exe run-examples
```

`lake build` checks every definition and proof: the 48 rules and their logged twins, soundness,
completeness and the theorems built on them, and one theorem per translated test program (each
shard's file prints how many, and how many are by the kernel). `lake exe run-examples` evaluates
every test program, in module form, with the two constant oracles, reads each check's label in
the log, and writes `../example-run.md` (a table per shard) and
`../example-run.json` (for the site), and prints a summary and any disagreement.
`node runner/compare-example-run.js OLD NEW` (from the repository root) compares two such runs.
`lake env lean scripts/check-axioms.lean` checks that every theorem uses only the standard axioms,
and the axioms of `native_decide` only when tagged `[native]`. A build from clean takes about a
minute and three quarters; its largest Lean process needs 3.2 GB and all of them together 10.4
GB (`scripts/measure-build.sh`, 2026-11-11, after plan step 5). After a change to the tests, run the translator first
(definition/tools/README.md).

## Encoding conventions

* Each rule is one constructor; its label is in its doc comment. The option
  convention (R6) and the sequences of `r:d-pat-con` use small auxiliary
  relations (`EvalExpOpt`, `EvalExpRowOpt`, `EvalValBindOpt`, `MatchPatOpt`,
  `MatchPatRowOpt`, `MatchAtPats`) whose constructors are `opt_none`,
  `opt_some`, `seq_nil` and `seq_cons`; they are not book rules.
* Finite maps are association lists. `f + g` puts `g` first and drops from `f`
  the keys of `g`; lookup takes the first binding.
* A constructor name carries its arity (`Con = name x arity`), since
  `arity(con)` is "the arity of con in the custom type of the value at hand".
* APPLY's set is a list of at most two members (only function equality has two; Debug.todo has
  none). The evaluator reads its oracle at each choice: `false` takes the first member, `true` the
  last, so the constant oracles `.const false` and `.const true` give the two results of function
  equality.
* Floats are Lean's `Float` (IEEE 754 binary64) for add, sub, mul, fdiv and
  negate, equality, order, min, max, clamp and sqrt. The conversions to Int saturate into
  [-2^63, 2^63 - 1] (`satOfFloat`, by `Float.toInt64`), NaN giving 0; `round` is floor x, plus 1
  when x - floor x >= 1/2 (exact). Float `pow` and the elementary functions follow the special
  lines of fig:dynamic-basis-pow and fig:dynamic-basis-elem in order; their last line, fl(f(x)), is
  the C library's rounding, which the book leaves to the implementation. `append` is string
  concatenation or list append; `Char.fromCode` gives U+FFFD (the encoding's `other(n)`) for an
  integer that is no Unicode scalar value; `Debug.toString` gives `showElm`.
* `Float.floor`, `Float.ceil`, the elementary functions, `Float.pow` and float printing are not
  reduced by the kernel, so a program that uses round, floor, ceiling, truncate, an elementary
  function, `^` at Float or `Debug.toString` is marked `native := true` by the translator and
  its theorem is proved by `native_decide` and tagged `[native]`; so is a program the memory budget
  moves (`budgetNative`: AppendTypeSplitTest and DeepEqualityTest).
* Number specialisation is done by the translator, which writes the examples
  after it: `SCon.int` for an integer constant at Int, `SCon.intF` for one at
  Float, and the copies of declarations used at Float named with `$`
  (`incF$Float`). The Elm texts of the basis are copied likewise: `abs$Float`
  in InitialBasis.lean.
* Top-level definitions of an example's module are placed in a `let` around
  the logged expression, and its custom types' constructors are bound in the
  environment (Chapter 7 is outside this encoding).
* An operator's value is read from the dynamic operator table OT_dyn
  (rule r:d-atexp-op as revised by audit X1); it is looked up in no
  environment.

## What the theorems say

Every generated theorem's docstring names what it trusts besides Lean's kernel
(plans/lean-full-definition.md, "The trust model"): `[parse]` (elm-syntax parses the test as Elm
does), `[elab]` (the translator's elaboration and number specialisation; retired on 2026-11-12, by step 10, for the 608 tests with a `spec_` theorem), `[params]` (the
implementation parameters: IntRange and norm as eco's), `[harness]` (the harness's `Html.text`
and the core library's interfaces, D2), `[library]` (elm/core 1.0.5's Elm text is the meaning of
the core library values the program uses, which the book does not bind: D2's harness assumption
extended to the dynamic values; on the `t_` and `mean_` theorems of the 28 programs that name one,
plans/library-elm-texts.md), `[principal]` (what the inference returns for the program
is principal, D11: the hypothesis `InferPrincipalFor`; retired on 2026-11-13, by step 11, for every
test), and `[native]` (the Lean compiler, for a theorem proved by
`native_decide`).

* `legal_<project>_<Test>` (Certs/, 622 compile-success tests): the program as written is legal
  (`LegalProgram`: the syntactic restrictions, and Chapter 9's static rules with each module
  elaborated by a principal derivation meeting the further restrictions), without hypothesis
  (`legal_of_W`, from a `wcheck_<project>_<Test>` theorem: the kernel runs step 11's proved
  inference W, Chapter 9's conditions and the further restrictions, with the context of a
  one-module program's imports read from `Certs/Ctx_*.lean`, `wCheck_of_ctx`); 11 large programs by
  `native_decide`.
* `spec_<project>_<Test>` (Certs/EndToEnd_*.lean, 608 translated tests): Lean's pipeline from the
  source (`endToEndW`: derived forms, step 11's W, the proved checker, number specialisation,
  erasure) gives the reduced program the translator wrote, so the theorems about it no longer rest
  on `[elab]`; it follows from `wcheck_` (`endToEndW_of_wCheck`), so the kernel runs the inference
  and the specialisation once per test;
  `mean_<project>_<Test>` (606; the other two stop at Debug.todo): the program has a meaning by
  r:p-program with both premises (`programSem_of_wCheck`, without hypothesis), its dynamic premise
  (`DynOf`) in the test basis with the core library `Lib.Btest` for a view and `Btest []` for a
  worker (`dynBasis`).
* `ident_<project>_<Test>` (608): the specialisation of the program is unique and is the reduced
  program the translator wrote (`ident_of_wCheck`, without hypothesis).
* `refuse_<project>_<Test>` (Certs/Refusals_*.lean, all 287 compile-error tests: 70 by steps 8 and
  9 and imports, 201 by step 11's core refutation, 15 by module-level W, 1 by W's type of `main`):
  the program is not legal, for every derivation.

* `evExp_sound`: a value of the evaluator is a value of the book's relation `EvalExp`;
  `evExp_sound_l`: with its log, of the logged relation `EvalExpL`.
* `EvalExpL.forget`, `EvalExp.lift` (and the same for all 17 relations): the logged relations are
  the book's with a log; the log is defined by the logged relation, in the order its rules fix,
  which is one of the orders the book allows (A57, A58).
* `EvalExpL.nostuck`: for a derivation with value v and log l, the evaluator at any oracle, fuel and
  index runs out of fuel, reads a choice, or gives exactly v and l. Hence `noValue_of_stuck` (a
  phrase on which the evaluator is stuck without reading a choice has no value in any derivation)
  and `evExp_unique` (a value found without reading a choice is the only one).
* `EvalExpL.complete`, `evExp_complete`: every derivation is found by the evaluator with some
  choices and fuel; `noValue_iff`: a phrase has no value exactly when no choices and fuel give one.
* `t_<project>_<Test>` (generated, one per translated test): the test as the program it is, its
  modules (the helper modules it imports from its project's sources, each after the modules it
  imports, then the test) evaluated by the rules of Chapter 7 and Chapter 9 (r:p-dyn-module,
  r:p-dyn-main) in the test basis with the core library, `Lib.Btest` (`Btest libME`: ME0's
  interfaces of `List`, `Maybe`, `Result` and `Tuple` extended by the values of 12 elm/core texts,
  `libME_eval`). For a test that runs, `ViewChecks Lib.Btest g.modules [c1, ...]`: some derivation of the program has a log that meets every check, each a
  statement about the log (decision D9): `.has p`, an entry with the check's label and a value its
  CHECK line describes (`Expect`, a structural value: numbers, characters, strings, lists,
  tuples, records, constructor values, functions), or with the label alone for a CHECK line
  without a value; `.run ps`, consecutive entries, for a CHECK with its CHECK-NEXT lines; and
  `.printed r`, a regular expression the printed log matches, for a CHECK line with `{{...}}` or
  a CHECK-SAME. CHECK-DAG is read as CHECK. For a test that stops at Debug.todo, `NoMeaning Lib.Btest
  g.modules` (`noMeaning_of_stuck`); the values it logs before it stops are reported by
  `run-examples` and are not theorems.
  The log is the logged relations' (decision D4), in the order their rules fix, which is one of
  the orders the book allows (A57, A58): a statement about consecutive entries states that the
  book allows that order, not that it fixes it. When the evaluator reads no choice of APPLY,
  `viewChecks_every` makes the statement hold of every derivation's log. Proved by the kernel
  (`decide +kernel`), or by `native_decide` when tagged `[native]` (a value only the C library
  computes, a statement about the printed log, or the memory budget). Every theorem's doc
  comment lists the program's source files and the trust it rests on: `[parse]` (elm-syntax's
  parser), `[elab]` (the translator's names, types and number specialisation, until steps 9 and
  10), `[harness]` (the test basis's `Html`, decision D2, whose `text` is the constructor `node`
  of arity 1), `[params]` (the parameters of the dynamic basis that a test's values do not
  depend on) and, for a program that names a core library value (`Program.library`), `[library]`.
* Chapter 8 (plan step 4): the 39 rules of tasks, encoding, decoding and messages are constructors;
  `enc_iff` and `dec_iff` make the book's Enc and Dec the structural functions `enc` and `dec`
  (decision D8); `taskRed_iff` and its corollaries prove the book's property of task reduction;
  `stepTaskL` and `recvL` are sound and complete for the logged relations; `enc_total` shows that
  every value of a payload type has a canonical encoding. The platform is empty (`platPrims`,
  `platMgrs`), a parameter of the definition (`[params]`). A float's bits and the rounding of
  `Float.ofScientific` are the C library's (Lean's Float is opaque to the kernel), so the few
  theorems about particular floats (A74, A88) are `native_decide` and tagged `[native]`.
* Chapter 9 (plan step 5): `t_<project>_<Test>` for a worker test (shard `Worker01`, 35 tests):
  `({ w with checks := [c1, ...] } : Prog.WorkerTest).Holds`, some execution the book allows,
  under the test's host, has a log that meets every check, where the log is the evaluation of the
  modules', then the start's, then each step's (D9). The host is `none`, or the test runner's echo
  (`echoOut` back to `echoIn`, in order) for a program that refers to both ports. Proved by
  `holds_of_run` from a run of the default scheduler (`run_sound`), by the kernel, or by
  `native_decide` for the five tests that use Debug.toString. The scheduler's default order of a
  batch's leaves is reversed (Appendix E records Elm/JS so); the guarantees of A86 and the rulings
  A62 to A81 are theorems of their own (Prog/Guarantees.lean, Prog/Rulings.lean).
* `a43_one_unique`: 1 ^ -1 has the value 1 and no other; `a51_one_choice`: `(\x -> x) == (\x -> x)`
  reads exactly one choice; `log_order_demo`: a log statement about two `Debug.log` calls.
* `a48_float`, `a48_int_max`, `a48_int_min`: APPLY(max) and APPLY(min) are
  IEEE 754-2019 maximum and minimum at floats in either argument order, and
  the comparison at Int.
* `a49_apply_float`, `a49_float_lo_gt_hi`, `a49_float_nan_bound`,
  `a49_float_signed_zero` (`native_decide`, floats compared as printed):
  at floats APPLY(clamp, lo, hi, x) is min (max x lo) hi with those
  operations, so `clamp 10 0 5` is +0, `clamp nan 1 0.5` is NaN and
  `clamp 0 1 -0` is +0. `a49_int_lo_gt_hi` (kernel) and
  `a49_int_apply_singleton`: at Int, `clamp 10 0 5` is 10, the elm/core
  text's result, and APPLY's set has that one member.
* `elmTexts_eval`: each Elm text of the fragment evaluates in E_K, by
  r:d-dec-nonrec, to the closure that InitialBasis.lean binds.
* `a44_conversions` (`native_decide`): round, floor, ceiling and truncate at 2.5, -2.5, NaN,
  the infinities and 1e300: `round` rounds a half upward and every conversion saturates, NaN
  giving 0. `a44_round_minus_half`: `round -2.5` is -2 by the rules from E0.
* `a43_*`, `a42_*`, `a51_true`, `a51_false`: the rulings stated directly;
  `a51_true` and `a51_false` show that `(\x -> x) == (\x -> x)` evaluates to
  both True and False.
